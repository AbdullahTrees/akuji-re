# akuji-re v1.0 — the milestone, and the constraint for what comes next

## What v1.0 is

The reconstruction plays **Akuji the Demon from the title screen to the credits
and the results screen**, completed start to finish on easy. Not a decompiler's
output that compiles — a Pascal source tree that produces a working game.

It is not a claim that the reconstruction is byte-equivalent to `akuji.exe`.
It is a claim that it is *playable and finishable*, and that every part of it
that has been checked against the original agrees.

### What backs it

| | |
|---|---|
| `tools/check.sh` | the full gate, green |
| `tools/emudiff.py handler_live` | **296 cases, 0 disagree** against the original under Ghidra emulation |
| `tools/coverage.py` | every game-layer function referenced in `src/` |
| `tools/table_extents.py` | 173 tables whose length is pinned from OUTSIDE the table |
| `notes/audited.md` | 149 game functions: 9 MATCHES, 3 FIXED, 15 PARTIAL, 75 EMUDIFF, **47 UNVERIFIED** |
| `notes/divergences.md` | 15 recorded divergences: 7 B, 4 C, 4 D |

**Read those last two rows honestly.** 47 game functions have never been
verified, 16 audited rows carry `BACKWARD OUTSTANDING`, and 32 of 36 component
rows are unverified. The divergence register holds only the *deliberate*
differences — category A, mistranslation, never appears there by design,
because those get fixed. Seven were found and fixed in the session that
produced v1.0 alone. There are certainly more.

## The constraint for the cleanup phase

The next phase is readability: better names, magic numbers turned into
constants with meaning, comments that answer why. The obvious constraint is
"the source must still compile to the same executable". **That is not
checkable as a file hash, and stating it that way would forbid the work.**

Both facts below were measured, not assumed:

* **The build carries DWARF.** Five sections (`/4`, `/19`, `/31`, `/45`,
  `/57`) hold it; `/19` alone is 21 MB of the 28 MB file, and it contains every
  identifier. Renaming one constant changed 75% of the file's bytes.
* **The whole-file hash is not stable even for identical source.** `lazbuild`
  recompiles only what changed, and the debug sections come out laid
  differently depending on which units were touched.

What *is* stable, checked both ways:

| edit | result |
|---|---|
| comment-only | every section identical |
| renaming a used constant | DWARF differs, **every real section identical** |
| rebuild after reverting | DWARF differs, **every real section identical** |

So the constraint is on the sections that become the running program:

```
.text  .data  .rdata  .pdata  .idata  .rsrc  .CRT
```

    python tools/samebinary.py            # do they still match v1.0?
    python tools/samebinary.py --record   # adopt a new baseline, deliberately

If those match, the machine code, the constants, the resources and the import
table are the same bytes, so the program behaves identically. Renaming,
re-commenting and introducing named constants all pass. Anything that moves
`.text` changed more than its name.

**A failure is not automatically a mistake.** Fixing a real defect *should*
move `.text`; then re-record the baseline and say why in the commit message.
What must not happen is `.text` moving without anyone noticing.

## Rules that still apply

`CLAUDE.md` governs. The two that bite hardest in a cleanup phase:

* **§3a — frozen rows.** `MATCHES`, `FIXED` and `PARTIAL` rows in
  `notes/audited.md` need approval before editing, then a re-audit.
  `EMUDIFF` rows need `tools/emudiff.py` re-run afterwards.
* **§3a-2 — comments answer WHY, the code answers WHAT.** Deleting a comment
  whose fact is not in the code loses the fact. Change the code first, then
  the comment becomes unnecessary.

And the one this project cannot absorb, from `notes/divergences.md`:

> A category B fix touches the component. A category A fix touches game code.
> Getting that backwards is the one mistake this project cannot absorb.
