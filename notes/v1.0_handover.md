# akuji-re v1.0 — the milestone, and the constraint for what comes next

## What v1.0 is

The reconstruction plays **Akuji the Demon from the title screen to the credits
and the results screen**, completed start to finish on easy. Not a decompiler's
output that happens to compile — a Pascal source tree that produces a working
game.

It is not a claim of byte-equivalence with `akuji_source.exe`. It is a claim that the
game is *playable and finishable*, and that everything checked against the
original agrees.

### What backs it

| | |
|---|---|
| `tools/check.sh` | the full gate, green |
| `tools/emudiff.py handler_live` | **296 cases, 0 disagree** against the original under Ghidra emulation |
| `tools/coverage.py` | every game-layer function referenced in `src/` |
| `tools/table_extents.py` | 173 tables whose length is pinned from OUTSIDE the table |
| `notes/audited.md` | 149 game functions: 9 MATCHES, 3 FIXED, 15 PARTIAL, 75 EMUDIFF, **47 UNVERIFIED** |
| `notes/divergences.md` | 15 recorded divergences: 7 B, 4 C, 4 D |

**Read those last two rows honestly.** 47 game functions have never been
verified, 16 audited rows carry `BACKWARD OUTSTANDING`, and 32 of 36 component
rows are unverified. The divergence register holds only the *deliberate*
differences — category A, mistranslation, never appears there by design,
because those get fixed. Seven were found and fixed in the session that
produced v1.0 alone, including an entire missing phase of the ending. Expect
more.

# THE CONSTRAINT

**The code sections must be byte-identical to v1.0. The debug sections need
not be.**

```
.text  .data  .rdata  .pdata  .idata  .rsrc  .CRT
```

    python tools/samebinary.py             # did anything move?
    python tools/samebinary.py --where     # ...and which functions
    python tools/samebinary.py --record    # adopt this build as the baseline

Those are the sections that become the running program: the instructions, the
constants, the resources, the import table. If they match, the program *is* the
program. The DWARF sections (`/4`, `/19`, `/31`, `/45`, `/57`) are excluded
because they carry identifiers and line numbers, which is exactly what this
phase is meant to change.

### Why it is not a hash of the file

Both measured, not assumed:

* **The build carries 21 MB of DWARF** — section `/19` alone, of a 28 MB file
  — and it contains every identifier. Renaming one constant changed **75% of
  the file's bytes** while changing no code.
* **The whole-file hash is not stable even for identical source.** `lazbuild`
  recompiles only what changed, and the debug sections come out laid
  differently depending on which units were touched.

A file hash would therefore forbid renaming *and* fail at random.

# WHAT IS FREE AND WHAT COSTS

Measured against v1.0 with `tools/samebinary.py`:

| example of edits | `.text` | cost |
|---|---|---|
| comments, in any quantity | unchanged | **free** |
| renaming a constant, variable, function or unit symbol | unchanged | **free** |
| replacing a literal with a named constant of the same value | unchanged | **free** |
| introducing a local variable to hold a subexpression | **CHANGED** | exception |
| extracting a helper function | **CHANGED** | exception |
| reordering statements, even with identical side effects | **CHANGED** | exception |

The pattern: **anything the compiler resolves before it emits code is free;
anything that changes what it emits is not.** This is a debug build with
optimisation off, so the compiler will not absorb a redundant local for you.

That is good news for the bulk of the work. Naming magic numbers — the single
biggest readability win left — is free, and so is every rename and every
comment. Run `tools/samebinary.py` after each batch and it stays honest.

# THE EXCEPTIONS

There are two kinds of reason to move `.text`. **One is allowed. One is not.**

## Kind 1 — fixing an infidelity. ALLOWED.

v1.0 does not faithfully replicate the source binary at some point, and you somehow discovered it and are
fixing it. `.text` moving is then *correct*, and the baseline moves with it.

This is the good kind, and the phase should expect it: 47 game functions have
never been verified, so reading one properly will sometimes turn up a real
difference. That is the work, not an interruption to it.

### What it takes

1. **Ask the user. Every time.** Permission is not implied by the change being
   correct. Same rule as `CLAUDE.md` §3a for frozen rows.

2. **Prove it against the source binary in Ghidra — the DISASSEMBLY, not the
   decompiler's output.** This project has been burned three times by
   decompiled shape:
   * a signed `div 4` that FPC emits as `+3; sar 2`, transcribed as `shr` —
     which is a *logical* shift in Pascal and produced `$3FFFFFFF` from `-1`;
   * `CompareStr`, whose answer lives in FLAGS, so Ghidra invents a stale
     boolean for the branch — 26 functions affected;
   * `Fader_Tick`, whose draw-then-advance ORDER only the instructions settle,
     and getting it backwards cost a visible transition bug.

   Quote the addresses and the instructions in the commit message.

3. **Re-run what covers it.** `tools/check.sh` always; `tools/emudiff.py
   handler_live` if an `EMUDIFF` row was touched; `tools/samebinary.py --where`
   to confirm *only* the intended functions moved.

4. **Re-record the baseline** with `--record`, and say why in the commit.

### The retest, tiered by blast radius

A fidelity fix moves toward the binary — but it can still break the game,
because the surrounding code may have been compensating for the old behaviour.
**This is not hypothetical.** The `Fader_Tick` fix in the v1.0 session was a
pure fidelity fix, provably correct against the instructions, and it broke room
transitions: the old room stayed visible for three frames and the music changed
early. It was found by a human playing, not by any tool here.

So scale the retest to what the fix can reach:

| where the fix lands | retest |
|---|---|
| one entity handler | the stages that place that type — `tools/entity_usage.py --type NN` lists them |
| one screen (title, options, game-over, ending) | that screen, start to finish |
| the event interpreter or a stage transition | a save either side of a door, plus one room change |
| **a shared component** — fader, input, sprite pool, tilemap, audio | **full playthrough** |

Only the last row costs a complete run, and it is the row that has actually
bitten. A handler fix does not need one.

**Batch the expensive ones.** If several fixes land in shared components,
gather them, re-record once, and pay for one playthrough rather than one each.

## Kind 2 — restructuring for cleanliness, at the cost of some behaviour. NOT ALLOWED.

Reorganising calls into a shape that reads better, where the result is *nearly*
the same, is out of scope for this phase. Three reasons, in order of weight:

**We cannot measure "a little".** `emudiff` is 296 synthetic handler cases;
`check.sh` is structural. Neither can tell you a boss fight breaks three hours
in. The only oracle that catches behavioural drift is a human playing the whole
game, and that is precisely the thing too expensive to run per change.

**Matching v1.0 is not the same as being right.** This is the difference
between us and the matching decompilations — pret's `pokered`, `pokeemerald`
and the rest. **They match the original artefact:** any clean rewrite that
still produces the ROM is *proven* equivalent to the real game. **We would be
matching v1.0 — our own approximation**, with 47 unverified functions in it.
Matching v1.0 proves no regression *from v1.0*. It proves nothing about Akuji.
So a behavioural concession here is not measured against the game; it is
measured against a reconstruction that is itself unfinished.

**It is not how those projects got clean code.** pret never accepts a
behavioural concession. Their discipline is the opposite: when clean code does
not match, they keep hunting for a clean formulation that *does*, and where the
original is genuinely perverse they **document the quirk and reproduce it**.
Their cleanliness is bought with search effort, never with drift.

### What to do instead when clean code will not match

In order:

1. **Look for a formulation that matches.** The compiler is deterministic; a
   different-but-equivalent Pascal shape often emits the same code. This is the
   pret method and it is usually where the win is.
2. **If none matches, the ugliness is load-bearing — keep it and name it.**
   Buy the readability with a named constant, a better variable name, and a
   comment saying *why* the shape is what it is. All three are free.
3. **If the ugliness exists because the reconstruction is wrong, that is Kind 1**
   — a fidelity fix, with the process above.
4. **Ask the user what to do** - if a small change in behavior can result in significant positive changes to the codebase, prompt the user on what to do.

The test, applied honestly: *can you point at the disassembly and say the new
shape is at least as faithful as the old one?* If the answer is "it is not more
faithful, only prettier", and it moves `.text`, it does not happen.

# RULES THAT STILL APPLY

`CLAUDE.md` governs. The two that bite hardest in a cleanup phase:

* **§3a — frozen rows.** `MATCHES`, `FIXED` and `PARTIAL` rows in
  `notes/audited.md` need approval before editing, then a re-audit. `EMUDIFF`
  rows need `tools/emudiff.py` re-run afterwards.
* **§3a-2 — comments answer WHY, the code answers WHAT.** Deleting a comment
  whose fact is not in the code loses the fact. Change the code first; then the
  comment becomes unnecessary. Deleting is the second choice, never the first.

And the one this project cannot absorb, from `notes/divergences.md`:

> A category B fix touches the component. A category A fix touches game code.
> Getting that backwards is the one mistake this project cannot absorb.
